# 模型切换与自动分批

两条工作流的业务节点不依赖千问。换模型通常不需要重新设计归属、抽取和审核流程，但必须同步模型预算及提供商参数。系统不会根据 API Key 自动识别底层模型。

## 预算配置

`.env` 中 `AI_LOCAL_*` 和 `AI_EXTERNAL_*` 是两组独立配置。网页选择“本地 / 内网”或“外部”时使用对应配置，失败不会自动切换模型。`MODEL` 是运维标签，不会替你修改 Dify 节点中的模型。

| 配置后缀 | 用途 |
| --- | --- |
| `MODEL` | 记录实际模型名称，便于任务追踪 |
| `TOKENIZER_KIND` | `hf_json` 读取本地 Hugging Face tokenizer.json；`utf8_upper_bound` 按 UTF-8 字节数保守估算正文 Token |
| `TOKENIZER_FILE` | 容器内分词器路径，仅 `hf_json` 使用 |
| `CONTEXT_TOKENS` | 实际部署允许的上下文长度，不能只按模型宣传的最大值填写 |
| `TOPIC_OUTPUT_TOKENS` | 每次归属输出预留，默认 1800 |
| `RECORD_OUTPUT_TOKENS` | 每次抽取输出预留，默认 2600 |

当前本地使用固定版本的千问分词器，来源与 SHA256 见 `backend/tokenizers/qwen3-vl.source.json`。计数覆盖精简后的 System、User、消息、候选问题及 ChatML 包装；8192 上下文另预留 512 Token 校正空间和 256 Token 安全空间。归属可用输入 5624，抽取可用输入 4824。

其他模型有对应 `tokenizer.json` 时，可挂载文件并更改路径；聊天模板与提供商额外包装也会影响实际用量，不能将任意模型的计数都称为精确计数。暂未接入匹配分词器时，使用 `utf8_upper_bound` 会使批次偏小，适用于常见字节级分词的保守估算，仍须用实际提供商验证，不能保证所有专有分词器都满足同一上界。应先采用保守的有效上下文值。如果保守估算连固定提示词都超预算，系统会拒绝请求，需要接入匹配分词器或使用实际支持的更大上下文，不能仅为通过检查而虚增上下文数值。

## 更换模型的操作

1. 等当前任务完成，或在 AI 任务中取消并保留断点。
2. 在两条 Dify 应用的抽取、修正 LLM 节点都选择新模型。相同 Ollama 提供商通常可保留现有参数绑定；其他提供商需要移除不支持的 `num_ctx/num_predict/num_gpu/json_schema`，选择对应的输出长度及 JSON 输出方式。节点连接和输入输出协议保持不变。
3. 更新对应 `.env` 配置并发布两条 Dify 应用。模型服务的实际上下文、Dify 凭据限制与应用输出限制需要一致。
4. 执行 `docker compose up -d --no-deps --force-recreate api worker beat`，让服务读取新环境。
5. 使用合成样例创建新任务，确认两条流程都生成草稿后再处理业务文件。

`scripts/build_dify_dsl.py --provider <提供商ID> --model <模型名>` 可生成相同业务图的模板。Ollama 生成专用参数，其他提供商仅生成通用 `temperature/max_tokens`，导入后仍须核对该插件支持的参数与结构化输出能力。生成文件本身不会更新已发布应用。

已开始任务冻结预算和输入快照，并记录每个阶段实际观察到的 Dify 工作流版本。续跑发现已发布版本变化时，会拒绝应用新结果并提示创建新任务；不把新旧模型的结果混入同一任务。已成功的步骤保留。尚未开始某阶段时，记录它第一次使用的发布版本。

## 长记录与恢复

归属按 Token 和输出容量共同打包，最多附带两段前文，从同群全部问题检索候选。原文过长时按 Unicode 码点无损切片，同一条消息的多个片段分别处理，之前的有效问题关联继续保留。候选检索是启发式检索，跨批次的业务归属仍需人工核对。

归属输出即使经一次 Dify 修正仍不合格，后台会二分批次；单片段仍不合格时，仅明确业务问题、规则、字段/SQL逻辑等保留待人工归属。事务性回复不因模型失败一律转人工，原文始终保留。缩小后的批次容量保存在断点中，连续三批成功才逐步加一；Token 和输出预算始终是硬上限。任务卡片的待确认数量是结束时快照，当前队列以聊天筛选结果为准。

抽取对超预算问题执行分段事实提取，再以原文证据窗口汇总。不同位置的引文以独立视图保留，不伪造拼接原文。所有片段处理完成后才请求最终 QA，分段临时结论不直接发布知识。最多四层压缩仍无法容纳时明确失败，保留步骤结果供续跑和人工处理。

PostgreSQL 持久化原文范围、游标、问题关联、步骤输入、远端运行 ID 和结果应用标记。页面“从断点继续”复用成功步骤，Worker 重启后由 Beat 扫描恢复；业务写入受租约与 fencing token 保护，避免重复创建草稿。传输结果未知时优先查询既有 Dify 运行，无法确定时保留错误，不保证远端模型只执行一次。

原始导入限制仍是 10MB、20000 条消息；这与单次模型上下文预算不同。总耗时随批次数、模型速度和输出质量增加，不能把“可导入”理解成一次模型调用即可处理。
